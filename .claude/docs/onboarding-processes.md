# ReferralPlatform — onboarding GP, Specialist, and Justice Dept/social-services orgs, and what's still missing

*Prepared 13 August 2026*

## Making real use of PHNs — beyond funding

The funding angle already covered is one use of PHNs, but there's a bigger one worth building into the platform's actual design, not just the go-to-market plan.

**HealthPathways is the single biggest finding here, and it changes how the referral-creation module should work.** Most Australian PHNs license and run HealthPathways for their region — "an online clinical management and referral resource" that GPs use during consultations, which explicitly guides "when and where to refer patients, with guidance on what information is needed to maximise the quality of referrals and reduce waiting time for patients." ([HealthPathways — Murray PHN](https://murrayphn.org.au/focus-areas/digital-health/healthpathways/)) That's not a competitor to build around — it's the existing decision layer that already tells a GP where a given condition should be referred, in most regions of Australia. Don't rebuild that logic; integrate with it.

### How to actually do this — the confirmed integration mechanism

This isn't a hypothetical partnership — it's a proven, documented pattern with real integration partners already operating it:

- **HealthPathways publishes a free "Pathway Link API"** specifically for third-party vendor integration — described as enabling "seamless and reliable integration with third-party vendor systems," available at no cost to vendors, with vendors expected to apply for API access and review the API documentation rather than scraping or hand-building links. ([HealthPathways Platform Integrations](https://www.healthpathwayscommunity.org/About/HealthPathways-Platform-Integrations))
- **This exact pattern is already live**, not speculative. Two directly relevant precedents: **MEDrefer** — an Australian e-referral/specialist-booking system, i.e. a direct functional analog to ReferralPlatform's own referral-creation and specialist-matching modules — is a confirmed HealthPathways electronic-referral-system integration partner. And the **NHS e-Referral Service** (the UK system already studied for its combined referral+booking workflow) is also a confirmed HealthPathways integration partner, meaning the world's most mature single-workflow referral platform runs exactly this pattern in production. Separately, **Heidi** (an AI clinical-documentation/scribe startup) recently partnered with Streamliners (HealthPathways' operator) to embed HealthPathways content directly inside its AI documentation tool — a live example of a newer, AI-forward platform doing precisely the "surface the right pathway inline, at the point of clinical work" integration this project should aim for. ([Heidi/HealthPathways integration — Healthcare IT News](https://www.healthcareitnews.com/news/anz/heidi-integrate-healthpathways-and-more-briefs))
- **HealthPathways also separately confirms Healthdirect's National Health Services Directory (NHSD) as one of its own "Service Directory" integration partners** — an unprompted cross-validation of the NHSD-as-base-layer recommendation already made in the specialist directory doc; the two integrations (NHSD for the "who/where" and HealthPathways for the "when/where to refer") are designed to sit together in exactly the way this platform needs them to.

### Two concrete ways to use it, in increasing order of integration depth

1. **Phase 1 — deep link (low effort, ship first).** At the referral-creation step (step C1 in the business process flow), once the GP selects a reason/condition for referral, call the Pathway Link API for the patient's PHN region and surface a direct link into the matching HealthPathways page. No content duplication, no licensing complexity beyond API access — just points the GP at the guidance that's already authoritative for their region.
2. **Phase 2 — inline guidance (the Heidi pattern).** With the relevant PHN's cooperation, surface the pathway's actual "where to refer" recommendation inline in the referral-creation UI itself — auto-suggesting the specialist type/service HealthPathways indicates for that condition, before the GP even opens the specialist directory. This is a materially better UX than a link-out, and it's the same integration depth Heidi has already built, so it's a known-achievable target, not a research question.

### The one real constraint worth flagging

HealthPathways content is regionally licensed and edited — each PHN runs and customises its own regional instance, so a single central API integration gets ReferralPlatform *technically* connected everywhere, but the *content itself* still varies by PHN, and getting a PHN to actively support or promote the integration (rather than just tolerate it) still runs through the same regional PHN relationship already recommended as the adoption channel and pilot partner. Treat the API integration as the technical unlock and the PHN relationship as the adoption unlock — both are needed, and they're the same relationship already being built for other reasons.

This has been added to the regulator/partner questions list: apply to HealthPathways Community for Pathway Link API access and documentation, and confirm the regional content-licensing terms for the pilot PHN.

**PHNs are also the practical adoption channel, not just a funding source.** They already run practice support and digital-health-uplift programs for GPs in their region — training, change management, even specific grant programs like a "Cybersecurity Uplift Program" found in this research. ([PHN Cybersecurity Uplift Program Grant](https://thephn.com.au/news/strengthen-your-practices-cyber-security-phns-cyber-security-uplift-program-grant)) Getting listed as part of a PHN's existing digital-health-uplift program is a far cheaper way to reach GPs than direct sales, and it comes with a trust signal a cold pitch doesn't — a program a GP's own PHN is actively promoting reads very differently from an unsolicited approach from a startup.

**And PHNs are the natural place to run a regional pilot** before attempting anything national — smaller, defined GP/specialist population, an existing relationship with the practices in that region, and a funder who's already motivated by exactly the outcomes (reduced unnecessary referrals, closed care gaps) this platform is built to produce.

## Onboarding process — GP practice

1. **Practice-level registration, not individual GP self-signup.** The practice (as an organisation) registers, verified against its HPI-O through the Healthcare Identifiers Service — this ties directly into the fraud-prevention design already covered: only HPI-O/NASH-authenticated practice systems can trigger new patient accounts or referrals, closing the "fake GP practice" fraud surface.
2. **Integration tier selection**, matching the tiers already scoped in the competitive/integration research: start at Tier A (structured booking requests, no deep integration) for a fast start, with Tier B (practice-software connection via existing secure messaging rails) as the real target, and Tier C (native "send to ReferralPlatform" button inside their practice software) as the long-term state once there's enough platform traction to justify the vendor partnership work.
3. **Calendar connection** for the booking module — Google/Outlook/CalDAV free-busy sharing, the lightweight mechanism already recommended, so a practice can start using the booking module the same day regardless of which PMS they run underneath.
4. **MyMedicare and IHI resolution** riding on the same practice-software connection from step 2, rather than being separate onboarding steps.
5. **Compliance training/acknowledgement** for the compliance-checklist feature (child/DV/complex referral prompts) — the practice should formally acknowledge this is decision support, not a legal certification, before it's switched on for their referrals.
6. **PHN-channel onboarding as the preferred path where available** — if the practice's local PHN is a platform partner, route onboarding through that relationship (training, support, credibility) rather than a pure self-service signup.

## Onboarding process — Specialist

1. **Individual practitioner verification against AHPRA's public register** (the free, individual, on-demand lookup already scoped — not a bulk pull) to confirm current registration and specialty before any account is activated.
2. **HPI-I resolution** through the same Healthcare Identifiers Service used for patients' IHIs and practices' HPI-Os — this is what makes the specialist an addressable, authenticated party for secure messaging and for the audit-log signing described earlier.
3. **NASH-backed credential setup**, either the specialist's own existing NASH credential (if their practice already has one) or a new one issued against their HPI-I — this is what lets "specialist responds with advice" generate a genuinely signed, non-repudiable audit entry, not just a database row.
4. **Directory profile — self-maintained, not purely synced.** As already recommended, once a specialist is active, their own listing (location, consulting days, subspecialty) supersedes whatever was pulled from NHSD, since that will always have gaps for any specific individual.
5. **Calendar connection**, same lightweight mechanism as the GP side.
6. **Explicit opt-in to the eConsult/advice-only pathway**, since this changes their workflow and their Medicare billing pattern (a genuinely separate decision from "will you take bookings through this platform" — some specialists may want one without the other).

## Onboarding process — Justice Department / social-services organisations (Phase 2)

Worth being explicit that this is a materially different onboarding process, not a variant of the health one — it runs on a different legal basis entirely, as already flagged in the Phase 2 document.

1. **Organisational recognition under the relevant state scheme first, before any technical onboarding.** The organisation needs to actually be a formally prescribed "information sharing entity" (or equivalent) under whichever state scheme applies — that's a government recognition process external to the platform, not something the platform can grant. Onboarding should require evidence of that recognition as a precondition, not assume it.
2. **A different consent/authority model configured per organisation**, using the pluggable policy-layer architecture already recommended — statutory mandatory-sharing basis rather than the patient-consent model used for health, and it needs to be clear in the platform which basis applies to which organisation's referrals so the two never get silently conflated.
3. **A formal data-sharing/use agreement specific to this domain**, separate from whatever terms a GP practice or specialist agrees to — this is the kind of document that needs the dedicated legal workstream already flagged in the Phase 2 document, not a boilerplate terms-of-service checkbox.
4. **Given the different risk profile, this almost certainly needs a human onboarding/review step**, not self-service signup — verifying the organisation's statutory status and data-handling capability before granting access to anything.

## What's missing — worth resolving before locking the business process flow

A few gaps worth naming honestly before moving into formal requirements, roughly in order of how much they'd change the flow if addressed:

- **Minors as primary patients, not just as dependents of a carer.** Everything designed so far assumes an adult patient with an optional carer/delegate. A child who is themselves the patient — their own account model, parental/guardian consent authority, and what happens at age 18 (transition to their own independent account) — hasn't been designed at all, and it's a significant gap given how much attention child-safety got in the Phase 2/justice context specifically.
- **The tension between the immutable audit log and a patient's right to have their data corrected or deleted.** Worth resolving now rather than discovering it during a real deletion request: the standard technique is **crypto-shredding** — encrypt sensitive fields with per-user (or per-record) keys, and "delete" by destroying the key rather than the log entry itself. The tamper-evident chain stays intact (nothing is removed from the ledger, so audit integrity holds), but the data becomes permanently unreadable once the key is gone — which is generally accepted as equivalent to deletion for privacy-compliance purposes. Worth designing the audit log with this in mind from the start rather than retrofitting it.
- **Exception and error paths.** What happens when a referral is declined by the specialist as inappropriate, when the 2-day activation queue expires with no patient response, when a booking preference can't be matched at all, when a patient wants to cancel a referral entirely — none of these are on the current flow, which only shows the success path.
- **A genuinely urgent/emergency bypass.** The booking module's preference-matching is designed for routine care; a clinically urgent referral needs a distinct, faster path that skips preference negotiation entirely, and the flow doesn't currently distinguish the two.
- **Interstate patient movement.** A patient's data and consent obligations may shift if they move states mid-referral relationship — relevant given the state-by-state information-sharing research already done, and worth at least flagging even though it's more acute for the Phase 2 domain than core health referrals.
- **Complaints and dispute resolution.** No path yet for a patient disputing a referral decision, a compliance-flag outcome, or a specialist's conduct — worth deciding whether this routes to existing bodies (AHPRA, state health complaints commissions) or needs its own in-platform process.
- **Business continuity.** This sits in an active clinical pathway — what happens to in-flight referrals and follow-up plans if the platform has an outage, and what's the data-continuity commitment if the company itself doesn't continue — is worth a real answer before this is trusted with real patients, not an afterthought.
- **Deceased patient data handling** — a genuine, if uncomfortable, workflow every health record system eventually needs.
- **Professional indemnity implications for GPs and specialists using a new platform** — worth raising with a medical indemnity insurer or the relevant medical defence organisation before launch, since this hasn't been checked at all yet.
- **A traceability matrix back to the original six benefits** in the project brief (patient paperlessness, GP traceability, specialist efficiency, MyGov single connection, AI enablement, patient consent control) — worth doing once formal requirements start, so every module can be checked against what the project actually set out to achieve, not just against what's accumulated through iteration.

# Referral Platform — patient-centered recall, automated pathology verification, and AI-assisted intake

*Prepared 13 August 2026*

## The reframing matters and should be stated as a design principle

Worth writing down explicitly, because it changes how every feature so far should be built: the patient (and carer) is the primary user, and the GP/specialist-facing surfaces are secondary views that feed into the patient's own record — not the other way around. Practice software (Best Practice, MedicalDirector) is built to run a clinic; this platform should be built to run a patient's care journey across clinics. Concretely, that means the "Follow-up Plan" object from the last round of ideas should live first in the patient's own timeline (with plain-language explanations, not clinical shorthand), with the GP notification as a supporting side-effect — not a GP-side recall system that happens to also ping the patient. Small distinction, but it should drive UI and data-model decisions throughout, and it's also the platform's real point of differentiation from the incumbents, who are all provider-facing by design (see the earlier competitive analysis — none of HealthLink, Medical-Objects, ReferralNet, or Argus have a patient account at all).

## How to actually verify a blood test was done, not just remind and hope

Two layers, worth building in this order:

**Layer 1 — reminder plus self-report (ship first, zero integration cost).** Push notification/SMS X days before the due date, with a simple "done" button. Cheap, immediate, and useful even after Layer 2 exists — some tests will be done at a private or interstate lab outside whatever automated rail you connect to, so self-report is a permanent fallback, not just an MVP stopgap.

**Layer 2 — automated detection via the pathology e-ordering/e-results rail.** This is the real answer to "if we had an automated feature to check this it would be better," and it's achievable because the infrastructure already exists and is mature — Australian pathology providers already return results electronically to the ordering clinician through the same secure messaging networks used for referrals (HealthLink, Medical-Objects, ReferralNet), and PHNs actively promote "eOrdering/eRequesting" as a mainstream general practice feature already. ([Electronic Pathology Requests — Western Vic PHN](https://westvicphn.com.au/health-professionals/health-topics/digital-health/electronic-pathology-requests/), [eOrders/eRequests — DDWMPHN](https://www.ddwmphn.com.au/eorders-or-erequests)) Two ways to plug into that, in order of how much you control:

1. **Platform originates the request.** When the specialist sets a Follow-up Plan item (e.g., "FBC and LFTs, 2 weeks before September 2027 review"), the platform generates the electronic pathology request itself and routes it through one of the existing secure messaging rails, on the GP's or specialist's behalf. The result then comes back to the platform on the same channel the moment the lab processes it — genuinely automatic detection, no patient action required at all.
2. **Platform receives a copy, GP's system stays unchanged.** If you don't want to insert yourself into the ordering step (less disruption to existing GP workflow, faster to get GPs comfortable with), register the platform as an additional recipient on the result message — most secure messaging networks support routing a result to more than one destination — or, more simply, detect the result via **My Health Record**, since pathology results are one of the document types that already flow into it. With the patient's consent, the platform periodically checks My Health Record for a matching result near the due date and marks the Follow-up Plan item complete automatically when it appears. This is the lighter-weight build and probably the right v1 — it reuses the same My Health Record conformance pathway already flagged as a to-do with ADHA for the referral-document side of the platform, so it's incremental work, not a second integration project.

Either way, **make this an explicit, named, revocable consent category** on the patient's consent page — "let ReferralPlatform check for pathology results related to my upcoming specialist reviews" — rather than something that happens invisibly. That keeps it consistent with the patient-controlled consent model already designed, and it's the kind of specific, well-scoped consent request that's much easier for a patient to understand and trust than a blanket "share my health data" toggle.

## Real-world precedent — you're not proposing something novel, which is good news

Three existing Australian (and one international) examples validate this pattern is provable, not speculative:

- **The National Cancer Screening Register (NCSR)** is a live, government-run, national-scale version of exactly this idea, for cervical and bowel cancer screening. It's the kind of proof point worth citing directly to PHN/ADHA funders: a government body already runs automated reminder-and-recall for a health maintenance action at national scale, which is precisely the pattern being proposed here for specialist follow-up care. ([About the National Cervical Screening Program — Dept of Health](https://www.health.gov.au/our-work/national-cervical-screening-program/about-the-national-cervical-screening-program?language=en), [The National Cancer Screening Register — Cancer Institute NSW](https://www.cancer.nsw.gov.au/prevention-and-screening/screening-and-early-detection/cervical-screening/about-the-national-cervical-screening-program/the-national-cancer-screening-register), [MJA — Supporting health care providers in cancer screening](https://www.mja.com.au/journal/2023/219/3/supporting-health-care-providers-cancer-screening-role-national-cancer-screening))
- **MedAdvisor**, an ASX-listed Australian company, runs medication adherence reminders tied to pharmacy systems rather than pure self-report — the same "detect the real action through an existing data rail instead of trusting memory" pattern, applied to medications instead of pathology. Worth a direct look at their integration model as a reference, though I'd confirm the exact technical mechanism with them directly rather than from public marketing material. ([MedAdvisor](https://www.mymedadvisor.com/en-au/))
- **Population health / care-gap-closure platforms** in the US value-based care market (Innovaccer, Arcadia, and similar) solve a structurally identical problem for Accountable Care Organisations — automatically detecting whether a patient completed a recommended action (a screening, a follow-up test) using claims and EHR data, then triggering outreach. Worth a look as an adjacent, mature product category if you want more design patterns to borrow from, even though it's a different market structure (US claims-based) than Australia's.

## More patient-centered ideas worth adding to the roadmap

A few extensions that follow directly from putting the patient at the center rather than the GP practice:

- **A patient-owned document vault**, not just a pathology-specific reminder. The "keep the form safe" problem generalises — results, referral letters, specialist correspondence should live in one place the patient controls regardless of which GP or specialist they see next, rather than being scattered across whichever practice's system originated each document. This is also a stronger differentiator against My Health Record itself, which is document storage without much patient-facing usability.
- **One-tap action on reminders**, not just a notification. If a pathology provider offers online collection-centre booking (several of the majors do), deep-link the reminder straight into booking a slot, rather than "remember to go get this done" — removes a whole extra step for the patient.
- **Loop the consented carer into every reminder**, not just the patient — this was central to the very first identity/carer discussion in this project, and it should carry through here: if a carer has delegate access, they should get the same reminder, since in many of the cases this platform is designed for, the carer is the one actually managing appointments.
- **Plain-language translation of the specialist's note.** "FBC and LFTs" means nothing to most patients. An AI-generated plain-language version of what's needed and why ("a blood test to check your liver and blood counts are still normal") sitting next to the clinical version is a small, concrete piece of the "fully AI enabled" goal from the original project brief, and it's genuinely patient-centered rather than a gimmick.
- **Multi-channel reminders, not app-only.** Given this platform's own onboarding design already accounts for patients who need carer support, don't assume everyone will reliably see an app push notification — SMS and, for anyone who's missed multiple reminders, an actual phone call (human or AI, see below) as an escalating channel.

## The AI intake call idea

Worth doing, and it's a real, active product category now — not speculative. But it needs a specific shape to avoid a well-documented failure mode in this exact space.

**What already exists to point to:** AI voice agents for healthcare intake and front-desk automation are a real, growing vendor category in 2026 (Retell AI, Feather, and others offer this specifically for healthcare front-desk/intake use cases), and Australia already has a notable local player in adjacent AI-clinical-tooling — Heidi Health, an Australian AI medical scribe company, though its core product transcribes and summarises a real doctor-patient conversation rather than autonomously conducting one. Your idea — an AI that independently calls the patient and asks preliminary questions — is a step further than scribing, closer to the "conversational AI triage" category.

**The cautionary tale worth knowing before building this: Babylon Health.** The UK/international AI symptom-checker company collapsed in 2023 after a $221M loss on $1B revenue, but the more relevant part for you is the clinical credibility failure that preceded the financial one: independent researchers found its triage system's own sponsored study "does not offer convincing evidence that it can perform better than doctors in any realistic situation," and UK clinicians raised formal safety concerns with the medical device regulator. The lesson isn't "don't use AI for triage" — it's that bold claims about what an AI can safely determine clinically need independent validation and transparent evidence, not marketing. ([Babylon Health collapse raises questions about AI claims — Patient Daily](https://patientdaily.com/stories/675677880-babylon-health-collapse-raises-questions-about-ai-claims-across-industries))

**How to shape your version to stay on the right side of that lesson:**
- Scope the AI strictly to **administrative and preliminary symptom-gathering questions** — reason for the visit, duration, relevant history, availability — never diagnosis, triage prioritisation, or clinical advice. The GP makes every clinical judgment; the AI just gathers structured information ahead of time.
- Build **mandatory safety-net escalation logic**: specific red-flag responses (chest pain, suicidal ideation, breathing difficulty, and similar) should immediately break the script and trigger an urgent human callback, not continue the preliminary questionnaire. This needs clinical sign-off on the flag list, not just an engineering decision.
- Have the AI produce a **short structured summary with flags**, not just a recording the GP is expected to sit through — a GP re-listening to an 8-minute call to save themselves an 8-minute call defeats the point. The recording stays available if the GP wants to check something, but the default review artifact should be a 30-second summary, the same pattern AI scribes already use successfully.
- **Explicit disclosure that the patient is talking to an AI**, and **explicit consent to the call being recorded**, both captured before recording starts. This isn't just good practice — recording a phone conversation in NSW and Victoria generally requires all-party consent under each state's surveillance/listening-devices legislation, so the consent step is a legal requirement, not a courtesy. ([Surveillance Devices Act 2007 (NSW) — overview](https://en.wikipedia.org/wiki/Surveillance_Devices_Act_2007_(NSW)), [Victoria Recording Laws — Sprintlaw](https://sprintlaw.com.au/articles/victoria-recording-laws-legal-compliance-for-businesses/)) Get this specific point checked by a lawyer before launch — the exact exceptions and requirements vary by state and are exactly the kind of detail worth getting right rather than assuming.
- **Keep Medicare billing clean**: the AI call itself isn't the billable service — the GP's actual telehealth consultation is. Make sure the platform's design and any patient-facing language keeps that boundary unambiguous, so there's no confusion about what's being charged for what.

**On checking the 12-month telehealth relationship automatically — better mechanism than what you proposed.** Checking the platform's own interaction history is a reasonable instinct but an incomplete signal — the platform only sees referral-related touchpoints, not a patient's routine GP visits, so it would under-detect genuine ongoing relationships. There's a cleaner answer: as of November 2025, **MyMedicare enrolment itself now satisfies the continuity-of-care requirement and removes the 12-month rule entirely** for patients enrolled with their practice — this was a deliberate reform specifically to remove this exact administrative burden. ([No 12-month telehealth rule for MyMedicare patients — Medical Republic](https://www.medicalrepublic.com.au/no-12-month-telehealth-rule-for-mymedicare-patients/114143)) So rather than building your own eligibility inference, the platform should check (or simply ask/display) the patient's MyMedicare enrolment status with the relevant practice — if enrolled, the 12-month rule is moot; if not, that's a clear, specific, actionable prompt ("enrol in MyMedicare with your GP to unlock unlimited telehealth eligibility") rather than an opaque internal calculation.

## Follow-up: how do we actually check a patient's MyMedicare enrolment status?

Checked this directly, because "is there a real-time API" matters a lot for whether this is a five-minute lookup or a genuine integration project — and the honest answer is: not confirmed to exist as a public, automatable API today.

Services Australia's HPOS (Health Professional Online Services) is the tool GPs already use to check patient Medicare details, but based on what's publicly documented, it covers Medicare card validity, concession/DVA status, and care-plan history — MyMedicare enrolment status specifically isn't confirmed as one of the checks available there, and even the checks that are available are manual web-portal lookups after a PRODA login, not a machine-callable API. ([Patient details in HPOS — Services Australia](https://www.servicesaustralia.gov.au/patient-details-hpos?context=20)) Scraping or automating a PRODA-gated government web portal isn't a viable design path regardless — that's almost certainly against its terms of use and not something to build a product feature on top of.

What's actually more promising: **both MedicalDirector and Best Practice already have MyMedicare administration built into their practice software** — MedicalDirector has a documented "MyMedicare Administration" module and Best Practice has "MyMedicare Patient Registration" functionality. ([MyMedicare Administration in MedicalDirector](https://www.medicaldirector.com/news/practice-management/mymedicare-administration-in-medicaldirector-your-essential-guide), [MyMedicare Patient Registration — Best Practice](https://kb.bestpracticesoftware.com/bppremier/spectra/MedicareDVA/MyMedicare/MyMPatientRegistration.htm)) That means the GP's own practice software is already the authoritative record of a patient's MyMedicare enrolment — which is exactly the same practice-software integration already planned for referrals (the HL7/FHIR "Tier B/C" work discussed earlier). Rather than building a second integration against Medicare directly, the practical path is to pull the enrolment flag as an additional field through that same practice-software connection once it exists, rather than treating it as a separate project.

**Two more things worth doing regardless of that integration timeline:** ask ADHA directly, in the same partnership conversation already recommended, whether an accredited-software-vendor pathway exists for a real-time MyMedicare check — practice software vendors themselves must have *some* machine-readable way to register enrolments, even if it isn't publicly documented, so this is a concrete, specific question worth putting to them rather than assuming the answer either way. And in the meantime, the pragmatic v1 is simply asking the patient directly ("are you enrolled in MyMedicare with your GP practice?") with periodic reconfirmation — cheap, immediate, and honest about what it is: self-reported until a real integration exists.
